# 产品市场前景验证

## 目标

判断一个产品或服务是否值得继续投入。重点看三件事：

- 是否有人主动搜索这个问题。
- 是否已有竞品在收费或拿到明显使用量。
- 是否能找到具体买家、预算来源和购买触发点。

不要只给乐观判断。没有足够证据时，给 `PIVOT` 或“先做验证动作”，不要建议继续写更多功能。

## 触发后先做

1. 读用户提供的产品描述、调研报告、README、PRD、落地页或代码仓库。
2. 抽取这些字段：
   - 产品一句话：解决什么问题。
   - 目标买家：谁付钱，不只是谁使用。
   - 典型场景：什么时候会需要。
   - 替代方案：现在用什么解决。
   - 收费方式：订阅、一次性购买、服务费、按量、私有部署。
3. 如果产品定义模糊，先用现有材料做一个可验证版本，不要停下来写泛泛问题。只有买家、场景或收费方式完全无法推断时才问用户。
4. 对需要当前数据的内容，必须联网查证。市场、竞品、定价、搜索建议、工具可用性都属于当前数据。

## 验证流程

### 1. 商业验证工具

优先检查这些工具是否能直接提交 idea：

- Fluenta
- DontBuild.it
- BuildBet
- Market Verdict
- Trending Needs Analyzer
- 其它同类产品验证工具

记录每个工具的结果：

- `可跑完整报告`：摘录 verdict、评分、证据来源和限制。
- `需要登录/付费/验证码`：说明卡在哪里，不要绕过访问控制。
- `只能看公开页面`：只记录定位、定价、数据源和用户互动，不把营销文案当结论。
- `工具不可访问`：记录错误类型和时间，再用公开数据复刻它的方法。

### 2. 公开搜索需求

用 Google autocomplete、Google Trends 或可用的 SEO/API 工具查：

- 核心词：产品类别、问题词、买家词。
- 场景词：`for <buyer>`、`private deployment`、`on premise`、`pricing`、`alternative`、`open source` 等。
- 中文词：按行业和使用场景写，不要只直译英文。

判断方式：

- 搜索建议出现具体问题词，说明有自然查询。
- 搜索建议只有定义、论文、教程，说明更像技术学习需求，不一定是购买需求。
- 搜索量未知时不要编数，写“有/弱/未见明确搜索需求”。
- B2B 私有部署、咨询和陪跑类产品，搜索需求通常弱于实际购买需求；要结合竞品和客户触发点判断。

### 3. 社区和开发者讨论

按产品类型选择来源：

- Reddit：用户痛点、替代方案、付费抱怨。
- Hacker News：开发者、创业者、基础设施、B2B 工具讨论。
- GitHub：技术供给、开源替代品、star/fork、维护状态。
- Product Hunt/PeerPush/IndieHackers：独立产品、定价、发布反馈。
- App Store/Chrome Web Store/G2/Capterra：用户评论和竞品缺口。
- 小红书/公众号/抖音/知乎：中文 C 端、本地服务和教育消费。

不要只看数量。重点提取：

- 用户是否主动描述问题。
- 是否有人问“推荐什么工具”。
- 是否抱怨现有工具价格、复杂度、部署、安全、数据迁移。
- 讨论是否来自目标买家，而不是围观者。
- GitHub star 多代表技术兴趣，不等于付费需求。

### 4. 竞品和收费证据

至少查三类竞品：

- 直接竞品：同样产品、同样买家。
- 间接竞品：客户现在用来替代的工具、表格、人工服务、内部系统。
- 上游/下游平台：可能把这个功能做进去的成熟产品。

记录：

- 定价页、套餐、是否 `Contact sales`。
- 是否有企业版、私有部署、本地部署、白标、API。
- 客户案例、行业页面、合规说明。
- 流量、收入、融资、招聘、公开用户数，能查多少写多少。
- 如果竞品多但都很便宜，说明订阅空间可能小。
- 如果竞品多且有企业销售，说明市场存在，但进入方式要更垂直。

### 5. 开源验证器和自定义流程

可参考这些工具的思路，不要求每次都完整部署：

- `Business_Idea_Validator`：抓 Reddit/ProductHunt/小红书等讨论，用 LLM 提取痛点、竞品、风险和评分。需要第三方抓取和 LLM key。
- Exa company researcher 类项目：适合查公司、竞品、融资和公开资料。需要 Exa/LLM key。
- 自定义组合：Exa/Search API + Reddit/HN/GitHub + Google autocomplete/Trends + LLM 汇总。

如果本机没有对应 key，不要伪造报告。改用可访问的公开接口和搜索结果。

## 评分

给每项 `0-5` 分，并写一句理由：

| 维度 | 高分条件 |
| --- | --- |
| 搜索需求 | 有具体问题词、购买词、替代品词或中文场景词 |
| 痛点强度 | 用户主动抱怨、求推荐、描述损失或必须解决 |
| 付费能力 | 买家有预算，或现有替代方案已经收费 |
| 竞品收入 | 竞品有定价、企业销售、流量、收入或融资证据 |
| 进入缝隙 | 能避开巨头正面竞争，有明确人群、行业、部署方式或渠道 |
| 实现成本 | MVP 能在短时间验证，不依赖大规模数据或重销售 |
| 获客路径 | 能找到 5-20 个可触达买家、社区、关键词或渠道 |

总判断：

- `BUILD`：至少 5 项高于 3 分，并且有付费或竞品收入证据。
- `PIVOT`：问题存在，但买家、价格、定位或进入方式需要调整。
- `DON'T BUILD`：只有技术兴趣，没有购买证据；或竞品强、进入方式不清；或实现成本明显高于可验证收益。

## 输出格式

使用中文输出，除非用户明确要求英文。结构：

1. 先给结论：`BUILD` / `PIVOT` / `DON'T BUILD`，加一句话理由。
2. 给“我实际试了什么”：工具、接口、关键词、数据源、哪些跑通、哪些被登录/付费/验证码挡住。
3. 给证据表：搜索需求、社区讨论、GitHub/开源、竞品收费、买家触发点。
4. 给风险：不要超过 5 条，每条必须可行动或可验证。
5. 给下一步验证动作：优先是 landing page、5 个买家访谈、报价页、冷启动渠道、手工服务，不要默认建议继续开发功能。
6. 附来源链接。使用短链接标题，不要堆满整页。

## 写法约束

- 保守表达。没有数据就写“未查到”“弱证据”“需要访谈确认”。
- 区分“有人讨论”和“有人会付钱”。
- 区分“技术可行”和“商业值得做”。
- 不使用投资人 BP、课程销售页或空泛营销口吻。
- 不承诺收益。
- 不把工具宣传页上的说法当作事实，只能当作“该工具自称”或“页面显示”。
- 不绕过登录、付费墙、验证码或访问控制。
